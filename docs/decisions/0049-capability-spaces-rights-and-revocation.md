# 0049. Capability spaces, rights, badges and revocation

- **Status:** Proposed
- **Date:** 2026-11-25

## Context

[0002](0002-capability-security-model.md), rule 1 says capabilities can be copied with fewer rights, passed over IPC and revoked, and its Consequences say revocation needs careful design. A manager must be able to revoke the capabilities it handed out, including those of sessions that a new root of the authorization tree ends ([0015](0015-jwt-tokens-and-oidc-identity.md), rule 1; [0016](0016-authorization-sparse-merkle-tree.md), rule 6; [0019](0019-authzen-decision-protocol.md), rule 8). It must also be able to tell which session a call belongs to ([0015](0015-jwt-tokens-and-oidc-identity.md), rule 1). The POSIX personality's `fork` copies the capability table ([0012](0012-posix-compatibility-layer.md), rule 4).

The [design backlog, D15](../design/design-backlog.md#m2-kernel-objects) asks for the capability space's structure, the rights bits, how derived capabilities are tracked and how a manager tells sessions apart. Its options are seL4's CNodes, with a capability derivation tree and badges, or a flat handle table in Zircon's style. [0047](0047-the-kernel-follows-sel4.md) chose seL4's model.

seL4 has four rights: read, write, grant and grant-reply. A badge is a number that the holder of an unbadged endpoint capability writes into a copy of it. The kernel delivers the badge with every message sent through that copy, and the sender can't change it. Under MCS, a scheduling context also carries a badge. A seL4 message may name up to three extra capabilities, but the receiver has a single receive slot, so at most one capability is transferred.

In seL4, revoking a capability deletes its descendants but leaves the capability itself. Messages already queued with a badge are canceled by a separate operation, CancelBadgedSends. Untyped memory is a watermark allocator: space inside an untyped region can be retyped again only once every object made from that region is gone. seL4 also keeps the references a thread holds to other objects, such as its fault and timeout endpoints, as capability copies in the thread's own slots, so revocation reaches them.

Claude drafted this record from the project owner's choice of seL4 as the model, on 2026-11-25.

## Decision

1. **A capability space is a tree of CNodes**, as in seL4. A CNode is an array of 2^n capability slots, made by retyping untyped memory, and a capability address is resolved through the tree with seL4's guarded lookup. So a process can have a small, flat space or a deep, sparse one. Each thread names the root CNode of its space, and threads of one process normally share it. The [kernel specification](../design/kernel-specification.md#capability-spaces-and-lookup) gives the slot and lookup details.
2. **There are four rights: read, write, grant and grant-reply.** A copy may drop rights, never add them. Endpoints use the rights as seL4 does ([0054](0054-ipc-endpoints.md), rule 7). The [kernel specification](../design/kernel-specification.md#rights-by-object-type) says what read and write allow on every object type. These meanings are fixed here, because other records rely on them:
   - **Eventcounts:** read allows reading, waiting, adding the eventcount to a wait set and binding it to a thread. Write allows advancing it, and binding an interrupt handler to it, since the kernel then advances it ([0053](0053-eventcounts.md), rules 2, 4, 5 and 8; [0055](0055-interrupt-objects.md), rule 2).
   - **Threads:** read allows reading the thread's state and registers. Write allows controlling the thread: suspending and resuming it, changing its registers, debugging it, canceling its current wait, setting its fault and timeout endpoints, registering its IPC buffer and binding an eventcount to it ([0061](0061-debugging.md), rule 3; [0054](0054-ipc-endpoints.md), rules 3 and 6; [0056](0056-faults-and-page-fetch-deadlines.md), rule 1; [0053](0053-eventcounts.md), rule 5).
   - **Address spaces:** read allows reading resident memory, and listing the mappings as descriptions, with no capabilities. Write also allows mapping and unmapping, writing resident memory through writable mappings, and listing the mappings with a capability to each mapping's memory object ([0057](0057-memory-objects-and-the-pager-protocol.md), rule 3; [0061](0061-debugging.md), rule 3). That capability carries the read right, and the write right only if the mapping is writable. The POSIX process server uses it for `fork`.
   - **Memory objects:** read allows mapping the object readable or executable, and making a clone that reads through to it: a clone of an immutable or pager-backed object. Execute is an attribute of a mapping, not a right, as in seL4. Write also allows mapping the object writable, making a snapshot clone of an anonymous object, and decommitting a range of an anonymous object, any clone included ([0057](0057-memory-objects-and-the-pager-protocol.md), rules 3, 4 and 8). A clone is anonymous, so cloning a clone needs the write right on it, and the new clone must belong to that clone's job or a descendant, because it shares the frames the clone holds. Pages neither clone has written still read through to a pager-backed root ([0057](0057-memory-objects-and-the-pager-protocol.md), rule 4).
   - **Jobs:** making an object needs no capability to a job. An object belongs to the job whose untyped memory it is made from, as in seL4 ([0058](0058-jobs-and-budgets.md), rule 1). The one exception is a child job, which is made through its parent's capability, because it carves the parent's reservation, limit and CPU share. A job's capability controls the job: giving it memory, making child jobs, listing, stopping, resuming and ending its threads, and setting its limits ([0058](0058-jobs-and-budgets.md), rule 9). The job's manager, such as the process manager, keeps it. A process holds untyped memory of its job, not its job's capability. Which right each job operation needs is open ([kernel specification K53](../design/kernel-specification.md#k53-rights-on-a-jobs-capability)). Whatever answers it must let the memory server hold a capability that gives and takes back memory and does nothing else ([0058](0058-jobs-and-budgets.md), rule 9).
3. **Badges are 64 bits.** An endpoint badge is set once, when a holder of an unbadged endpoint capability makes a badged copy. Copies of a badged capability keep its badge, and the receiver gets the badge with every message. A scheduling context's badge is set when the context is configured, as in seL4 MCS, and timeout faults report it ([0051](0051-scheduling-timers-and-deadlines.md), rule 1; [0056](0056-faults-and-page-fetch-deadlines.md), rule 3).
4. **The kernel tracks every derivation, so revocation is complete.**
   - Each copy, badged copy, transfer and retype is recorded as a child of the capability it came from, as in seL4's capability derivation tree.
   - **Revoking** a capability deletes all its descendants, wherever they have been passed, and leaves the capability itself. **Deleting** a capability removes that one slot. Both are preemptible ([0052](0052-smp-bring-up-and-the-kernel-lock.md), rule 2).
   - **Every binding holds a capability.** When the kernel keeps a lasting reference to an object from a capability presented to it, it keeps a copy of that capability, recorded as its child. This covers a wait-set entry's eventcount, a thread's bound eventcount, its fault endpoint and its timeout endpoint, and an interrupt handler's eventcount. It also covers a mapping's memory object: Map keeps a copy of the memory-object capability presented, as the mapping's own, and revoking or deleting that copy unmaps the range, as revoking an seL4 frame capability unmaps the frame ([0057](0057-memory-objects-and-the-pager-protocol.md), rule 3). Revoking or deleting a binding's copy removes the binding, so a revoked session's eventcount stops reaching its client's wait sets, and a revoked memory-object capability stops reaching its client's address space. The [kernel specification](../design/kernel-specification.md#kernel-bindings-that-hold-capabilities) says where the copies live.
   - **The one exception is hardware state.** A revocation leaves in place an interrupt translation service (ITS) table that the hardware still uses ([0055](0055-interrupt-objects.md), rule 4). How the revocation reports that is open in the [kernel specification](../design/kernel-specification.md#derivation-and-revocation).
   - When the last capability to an object is deleted, the object is destroyed. Its memory can be retyped again once every object made from the same untyped piece is gone, as in seL4. That is why jobs hold memory in page-sized pieces ([0058](0058-jobs-and-budgets.md), rule 4). The objects the kernel makes at boot belong to no job and are never destroyed ([0048](0048-kernel-memory-and-address-spaces.md), rules 1 and 2).
5. **A manager tells sessions apart by badge.**
   - At bind, the manager makes a badged copy of its endpoint capability for the new session, keeps it, and hands the client a copy derived from it. The badge names the session.
   - **A session may have several badges.** The protocol method `session_dup` asks for another badge of the session the call came on, and the manager makes it in the same way ([0064](0064-the-call-header-and-wire-encoding.md), rule 8). The manager's badge table maps each badge to its session, and records the minor version fixed at bind and whether the session is remote ([0065](0065-typed-errors-and-minor-versions-on-the-wire.md), rule 12; [0066](0066-capability-parameters-and-server-streams.md), rule 4).
   - To release a badge, the manager revokes the copy it kept, which deletes that badge's copies wherever they were passed, cancels the sends queued under the badge, and deletes the kept copy, as in seL4. Only then may it reuse the badge, so no message from the old session is delivered under a new one.
   - `session_close` releases only the badge it is sent on. A session ends when its last badge is released, or when its token expires or it is revoked, and ending it releases every badge it has ([0066](0066-capability-parameters-and-server-streams.md), rule 5).
   - When a new root of the authorization tree revokes a branch ([0015](0015-jwt-tokens-and-oidc-identity.md), rule 1; [0019](0019-authzen-decision-protocol.md), rule 8), a manager uses its table from badges to the policies each session was bound under, and ends the sessions that relied on that branch.
6. **Capabilities move in messages, up to three per message.** Sending one needs the grant right on the endpoint, and a reply carries them only under the rule for replies ([0054](0054-ipc-endpoints.md), rule 7). This departs from seL4, which transfers at most one capability per message ([0047](0047-the-kernel-follows-sel4.md), rule 3).
7. **Copying a capability table is a library operation.**
   - The kernel interface library copies a capability space's slots one by one, as children of the originals, so revoking an original also reaches the copy. The kernel needs no table-copy call.
   - Capabilities that can't be derived, such as an untyped capability with children and the control capabilities, are skipped or refused. Which of the two is D95's choice, with the rest of what `fork` copies, including how binding credentials stay with the parent ([0025](0025-twelve-factor-app-contract.md), rule 5; the backlog's conflict between it and [0012](0012-posix-compatibility-layer.md), rule 4).
   - If measurements show that copying slot by slot is too slow, a batch call can be added to the raw system-call ABI without changing the interface ([0059](0059-the-kernel-interface-library.md), rule 2).

## Consequences

- **Revocation is complete, with two named gaps.** A manager can withdraw a session without the client's help. Every copy the client made or passed on goes, and so does every binding made from them, mappings included (rule 4). Once the manager has canceled badged sends, no message queued under the session's badge is delivered. A revocation leaves an ITS table the hardware still reads ([0055](0055-interrupt-objects.md), rule 4). And revoking an address-space capability doesn't reach the memory-object capabilities that listing its mappings yielded, which derive from each mapping's own copy instead ([0061](0061-debugging.md), rule 4; [kernel specification K42](../design/kernel-specification.md#k42-capabilities-yielded-by-listing)).
- **Managers need no per-call lookup to know the caller.** The badge arrives with the message, and the manager's own table maps it to the session's principal, version and policies ([0015](0015-jwt-tokens-and-oidc-identity.md), rule 1; [0019](0019-authzen-decision-protocol.md), rule 8).
- **Allocation and control are separate.** Holding a job's memory lets a process make objects in its job, but not child jobs. Only the job's manager can list or stop the job's threads, so two processes in one job can't reach each other's threads through it.
- **A manager pays memory for each badge of each session**, because the copies it keeps sit in its own capability space, made from its own untyped memory.
- **Freed memory returns in whole untyped pieces.** A destroyed object's space is reusable only when its untyped piece is empty ([0058](0058-jobs-and-budgets.md), rule 4).
- **Raw capabilities still never leave a node** ([0002](0002-capability-security-model.md), rule 5). Across nodes, the network server holds the capability and proxies for it.
- **Capability spaces cost memory, and the memory is charged to their job** ([0058](0058-jobs-and-budgets.md), rule 5).
- **D15 is settled.** The structure is rule 1, the rights rule 2, derivation tracking rule 4 and sessions rule 5. The slot layout, the rights on the remaining object types and the open mechanism questions are in the [kernel specification](../design/kernel-specification.md#open-questions). D13's capability-table copy is rule 7, and what `fork` copies stays with D95.
